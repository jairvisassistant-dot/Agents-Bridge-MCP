## CRITICAL

### CODE-01 — Dry-run mode comparte conexión SQLite entre threads

**Archivo**: `src/agent_bridge/state/database.py:150-158`  
**Línea**: 153

```python
def _connect(self) -> sqlite3.Connection:
    if self._dry_run:
        if self._memory_conn is None:
            self._memory_conn = sqlite3.connect(":memory:")
        return self._memory_conn  # ← compartida entre threads
```

**Problema**: En modo dry-run, `_memory_conn` es una única instancia de `sqlite3.Connection` compartida entre TODAS las llamadas a `_execute`, `_execute_write`, `with_transaction`, etc. Como todas estas pasan por `anyio.to_thread.run_sync` (thread pool), múltiples corrutinas concurrentes ejecutan SQL en la MISMA conexión desde DIFERENTES threads. `sqlite3.Connection` NO es thread-safe — esto causa crashes, corrupción de estado interno, y resultados erráticos.

**Impacto**: Race condition determinística en dry-run bajo concurrencia. Produce crashes intermitentes o datos incorrectos.

**Recomendación**: En dry-run, crear una nueva conexión `:memory:` por llamada (como hace el modo normal), o serializar todo acceso con un lock dedicado. Alternativamente, crear el `:memory:` una vez pero usar `check_same_thread=False` + serializar con un lock thread-safe.

## HIGH

### CODE-02 — Race condition en startup con múltiples conexiones SSE concurrentes

**Archivo**: `src/agent_bridge/state/database.py:167-193`  
**Línea**: 167

```python
def _initialize(self) -> None:
    conn = self._connect()
    conn.executescript(SCHEMA_SQL)
    conn.commit()
    cursor = conn.execute("SELECT value FROM _meta WHERE key = 'schema_version'")
    row = cursor.fetchone()
    current_version = int(row[0]) if row else 0
    if current_version < SCHEMA_VERSION:
        _run_migrations(conn, current_version)
        conn.execute("INSERT OR REPLACE INTO _meta ...")
        conn.commit()
```

**Problema**: `init_db()` se llama en cada conexión SSE (`server.py:104`). Si dos conexiones SSE llegan simultáneamente a un DB fresh (schema_version=0), AMBAS ven `current_version=0` y ejecutan migraciones. `ALTER TABLE ADD COLUMN` NO es idempotente — la segunda conexión falla con "duplicate column".

**Impacto**: La segunda conexión SSE falla con excepción no manejada, desconectando al cliente.

**Recomendación**: Usar `BEGIN IMMEDIATE` + `INSERT OR IGNORE` para schema_version como un lock de startup, o mover la inicialización/ migración a un singleton fuera del handler SSE.

### CODE-03 — JSON injection en `review.approve` vía `comment`

**Archivo**: `src/agent_bridge/tools/review.py:167`  
**Línea**: 167

```python
return [types.TextContent(
    type="text",
    text=f'{{"task_id": "{task_id}", "status": "approved", "comment": "{comment}"}}',

```

**Problema**: `comment` proviene de `args.get("comment", "")` — input del usuario (MCP tool arguments). Si el usuario envía un comment con `"` o `\`, rompe la estructura JSON. Ej: `comment = 'x", "injected": true'` → `{"task_id": "...", "status": "approved", "comment": "x", "injected": true}`.

**Impacto**: Permite inyectar campos falsos en la respuesta JSON. Dependiendo del cliente MCP, esto podría explotarse para manipular comportamiento aguas abajo.

**Recomendación**: Usar `json.dumps()` en lugar de f-strings para toda respuesta que incluya datos del usuario.

## MEDIUM

### CODE-08 — `asyncio.create_task` no tracked para mantenimiento

**Archivo**: `src/agent_bridge/server.py:280`  
**Línea**: 280

```python
asyncio.create_task(_maintenance_loop(db))
```

**Problema**: La tarea del maintenance loop se crea fire-and-forget. No hay referencia almacenada, no se cancela en shutdown. Si el servidor se detiene, la tarea sigue ejecutándose hasta que el event loop la cancele forzosamente. Además, mezcla `asyncio.create_task` con el ecosistema `anyio`.

**Impacto**: Tarea huérfana en shutdown. Sin garantía de terminación ordenada.

**Recomendación**: Almacenar la task y usar `anyio.start_task()` o un cancel scope. Cancelar explícitamente en shutdown (ej: mediante un `anyio.Event`).

### CODE-10 — MCPClient no verifica IDs de response

**Archivo**: `src/agent_bridge/ui/chat_tui.py:186-214`  
**Línea**: 205-211

```python
response_bytes = await asyncio.wait_for(
    self._process.stdout.readline(), timeout=30
)
return json.loads(response_bytes.decode("utf-8"))
```

**Problema**: `_msg_id` se incrementa pero la respuesta no se correlaciona con el request. Si un response timeout ocurre y se reintenta, o si el servidor envía un response fuera de orden (notifications with no id), los IDs se desincronizan permanentemente. **Recomendación**: Verificar `resp["id"] == self._msg_id - 1`. Usar un dict de pending requests keyed by id.

### CODE-14 — Sin timeout en operaciones DB

**Archivo**: `src/agent_bridge/state/database.py:238-268`

**Problema**: `anyio.to_thread.run_sync` se usa sin timeout. Si SQLite se bloquea (deadlock, lock prolongado), el thread worker queda bloqueado indefinidamente, agotando el pool de threads. Con `busy_timeout=5000`, un lock de 5s bloquearía el handler MCP por 5s.

**Impacto**: Potenciales freezes del servidor bajo alta contención.

**Recomendación**: Usar `anyio.to_thread.run_sync(func, cancellable=True)` con un `fail_after` timeout.

## Notas Adicionales

- **Async**: El código usa mayoritariamente `anyio.to_thread.run_sync` correctamente. Las excepciones son CODE-08 y CODE-09 que mezclan `asyncio.*` en un ecosistema anyio.
- **SQL Injection**: Todas las queries SQL usan parámetros `?`. Los placeholders generados dinámicamente en `get_plan_export` son seguros.
- **Race conditions**: `task.claim` y `task.submit_work` usan `UPDATE ... WHERE status = 'pending'` correctamente como lock atómico. El punto débil son CODE-06 y CODE-07.
- **Error handling**: El `handle_call_tool` envuelve todo en try/except y retorna errores estructurados con `request_id`. Todas las tools verifican existencia antes de operar.
- **TUI**: El MCPClient tiene manejo de reconexión con backoff exponencial (1s→30s max). Sin embargo, CODE-10 es un riesgo silencioso.
