Esta auditoría contrasta la **promesa del producto** (README + SPEC) contra el **comportamiento real del sistema** (código). El patrón dominante: el producto se vende como un broker MCP integrado con servidor SSE + TUI conectada, pero la realidad es que TUI y SSE server son procesos independientes que comparten archivo SQLite mediante polling.

---

## CRITICAL

### PROD-01 — `--ui-only` miente sobre su funcionamiento

**Archivo**: `src/agent_bridge/main.py:28-32` + `README.md:214`
**Severidad**: CRITICAL

**Descripción**: El flag `--ui-only` se describe como "Solo TUI (conectarse a server existente)" (README) / "Start only the TUI (connect to existing SSE server)" (CLI help). La realidad: el TUI spawns su PROPIO subproceso stdio de `agent_bridge` — NO se conecta al SSE server. Ambos procesos son independientes y lo único que comparten es el archivo SQLite.

**Impacto en confianza**: Un usuario que hace `agent-bridge start --headless` en terminal 1 y `agent-bridge start --ui-only` en terminal 2 cree que el TUI está conectado al SSE server. En realidad inicia un servidor MCP completamente separado. Si los paths de DB difieren, cada proceso opera sobre datos distintos sin advertencia. Engaña al operador sobre la topología real del sistema.

**Recomendación**: Renombrar a `--standalone` o `--tui-only` y documentar explícitamente que el TUI se conecta a la DB compartida, no al server SSE. O implementar conexión real via SSE desde el TUI al server existente.

### PROD-02 — README promete chat "en tiempo real" pero es polling a 5s

**Archivo**: `README.md:225-237` (diagrama de flujo) + `AGENT-BRIDGE-SPEC.md:37` ("en tiempo real")
**Severidad**: CRITICAL

**Descripción**: La SPEC promete "Los mensajes del chat llegan a ambos en tiempo real." La TUI usa polling cada 5s (`chat_tui.py:334`). Los agentes no reciben push — deben llamar `chat.read` explícitamente en cada ciclo. "Tiempo real" implica latencia <1s; 5s de polling + latencia de agente = >10s típico.

**Impacto en confianza**: Cuando un humano escribe `@desarrollador: pará, hacelo distinto`, la TUI muestra el mensaje inmediatamente (tras el send), pero el desarrollador NO lo ve hasta su próximo ciclo de trabajo. El humano cree que el agente recibió la instrucción; el agente sigue ejecutando. Falsa sensación de control inmediato.

**Recomendación**: Reemplazar "tiempo real" por "asincrónico con polling cada 5s" en docs. Para baja latencia real, implementar SSE push desde el servidor hacia los clientes.

## HIGH

### PROD-03 — SPEC documenta `agent-bridge configure` que no existe

**Archivo**: `AGENT-BRIDGE-SPEC.md:246-249`
**Severidad**: HIGH

**Descripción**: La SPEC (documento rector) define 4 subcomandos de `configure`: `configure`, `configure --set`, `configure --list`, `configure --init`, con flags y descripciones detalladas. Ninguno existe en `main.py`. La configuración existe solo mediante `init` + edición manual de `bridge.json`.

**Impacto**: Cualquier lector de la SPEC asume que existe un CLI de configuración. Esto fuerza edición manual de JSON sin validación, lo que puede producir archivos malformados que el server carga silenciosamente (sin error claro).

**Recomendación**: Implementar `agent-bridge configure` o eliminar toda mención de la SPEC. Agregar validación de `bridge.json` al cargar.

### PROD-04 — @mention "no envía si offline" advierte pero no bloquea

**Archivo**: `src/agent_bridge/tools/chat.py:379-403`
**Severidad**: HIGH

**Descripción**: La SPEC (línea 192) dice textual: "@arquitecto → NO enviar si está offline → el server responde: 'Arquitecto está offline desde las 14:32. El mensaje quedó en su inbox.'" La implementación (`_send_message`) SIEMPRE inserta el mensaje en la DB y adjunta un warning en la respuesta. El mensaje se entrega al inbox pese al warning.

**Impacto**: El humano recibe un "warning" de vuelta, pero el servidor no lo ve como error, solo como metadata. Los agentes no tienen lógica para respetar el warning. El mensaje "no enviado" SÍ se envía. Promesa de seguridad rota.

**Recomendación**: Implementar el comportamiento documentado: rechazar el send si el target está offline (o documentar que la SPEC cambió y explicar por qué el warning es suficiente).

### PROD-05 — TUI pierde sincronización request/response silenciosamente

**Archivo**: `src/agent_bridge/ui/chat_tui.py:186-214`
**Severidad**: HIGH

**Descripción**: `MCPClient._request()` incrementa `_msg_id` pero no verifica `resp['id']` coincida. Si un request timeout causa reintento, los IDs se desincronizan. Un response para el request #5 se asigna al request #6. El TUI puede mostrar datos incorrectos sin advertencia visible — mensajes que no corresponden, agentes en estado equivocado, etc.

**Impacto UX**: El humano ve datos inconsistentes en la TUI. No hay manera de detectar el problema desde la interfaz. Pérdida de confianza en la información presentada.

**Recomendación**: Verificar `resp['id']` y/o usar dict de pending requests. En el TUI, agregar un indicador de "estado de conexión" visible y mostrar warning cuando se detecta desincronización.

### PROD-06 — Modo dry-run no es seguro bajo concurrencia

**Archivo**: `README.md:217` + `src/agent_bridge/state/database.py:150-158`
**Severidad**: HIGH

**Descripción**: `--dry-run` se describe como "Modo prueba (no escribe en DB)". En dry-run, se comparte una sola conexión `:memory:` entre TODAS las llamadas `anyio.to_thread.run_sync`. `sqlite3.Connection` NO es thread-safe. Múltiples threads ejecutando SQL simultáneamente en la misma conexión causan crashes y datos incorrectos.

**Impacto**: Un usuario que prueba el sistema con `--dry-run` puede ver errores de concurrencia que no existen en modo normal, o viceversa. El modo "seguro para testear" puede producir falsos positivos y erosionar confianza. La feature de testing miente.

**Recomendación**: Crear conexión `:memory:` nueva por llamada (como en modo normal) con `check_same_thread=False` + lock, o eliminar dry-run hasta que sea thread-safe.

### PROD-07 — Rol mutable vía heartbeat permite escalación de privilegios

**Archivo**: `src/agent_bridge/tools/agents.py:110-113` + `src/agent_bridge/server.py:70-76`
**Severidad**: HIGH

**Descripción**: `agent.heartbeat` acepta `role_hint` que sobrescribe el rol. Si un agente hace heartbeat con `role_hint=architect`, obtiene permisos de arquitecto. El sistema documenta permisos como inmutables ("cada tool checkea que el agente tenga el rol adecuado") pero el rol es dinámico.

**Impacto UX**: No hay warning visible cuando un agente cambia de rol. La TUI muestra el rol nuevo sin indicar que cambió. Un developer podría escalar a architect silenciosamente. Inconsistencia entre confianza percibida y seguridad real.

**Recomendación**: Congelar rol tras primer heartbeat. Mostrar cambio de rol en TUI con log visible. Agregar advertencia si el role_hint difiere del bridge.json.

## MEDIUM

### PROD-08 — TUI da up permanentemente tras agotar backoff

**Archivo**: `src/agent_bridge/ui/chat_tui.py:140-155`
**Severidad**: MEDIUM

**Descripción**: `_ensure_connected` implementa backoff 1→2→4→8→16→30s, pero al llegar a `backoff > MAX_BACKOFF` (30s), sale del loop y retorna `False` PERMANENTEMENTE. Todas las llamadas futuras devuelven `None` — el TUI deja de funcionar sin indicarlo en la status bar. No reintenta después del backoff.

**Impacto UX**: El usuario no sabe que el TUI se rindió. La status bar puede seguir mostrando estado viejo congelado (no hay timer que la actualice). El usuario cree que el sistema funciona pero no recibe datos nuevos. El único rescue es Ctrl+C y reiniciar.

**Recomendación**: Reintentar indefinidamente con intervalo fijo de 30s tras agotar backoff. Agregar indicador persistente en status bar con "RECONECTANDO..." y tiempo desde última conexión exitosa.

### PROD-09 — Diagrama de state machine no refleja el sistema real

**Archivo**: `README.md:505-512` + `AGENT-BRIDGE-SPEC.md:139-145`
**Severidad**: MEDIUM

**Descripción**: La máquina de estados README muestra `idle → planning → tasks_ready → in_progress → completed`. La SPEC muestra un diagrama diferente (`idle → planning → tasks_ready → in_progress → review → approved`). Ningún plan pasa por `planning` — `plan.create` inserta directo en `tasks_ready` (ARCH-08). La validación de transiciones se ejecuta POST-write solo para mensajes de error (ARCH-01). El modelo es decorativo.

**Impacto UX**: Cualquier usuario que lea la documentación para entender el flujo de trabajo obtiene un modelo incorrecto. No hay forma de saber desde afuera en qué estado real está el sistema. Las transiciones "planning" y "completed" son fantasmas.

**Recomendación**: Sincronizar el modelo documentado con el real. Si no existe el paso `planning`, eliminarlo. Agregar tool `plan.complete` si el estado `completed` es alcanzable.

### PROD-10 — TUI y SSE server son independientes sin comunicación directa

**Archivo**: `src/agent_bridge/main.py:40-71` + `src/agent_bridge/ui/chat_tui.py:92-105`
**Severidad**: MEDIUM

**Descripción**: La arquitectura tiene DOS servidores MCP compitiendo: el SSE server (subproceso) y el stdio server del TUI (subproceso del subproceso). No hay comunicación entre ellos. Si el SSE server crashea, el TUI no lo sabe. Si el subproceso stdio del TUI crashea, el SSE server no lo sabe. Comparten DB por archivo, no por protocolo.

**Impacto UX**: El humano puede estar viendo agentes online en la TUI (status bar) mientras el SSE server ya murió. O viceversa: el SSE server corre, los agentes chatean, pero el TUI está desconectado sin que el usuario sepa. No hay indicador de salud del server SSE en la TUI.

**Recomendación**: El TUI debería heartbear al SSE server directamente para verificar conectividad. O unificar en un solo proceso con Server-Sent Events como canal bidireccional.

### PROD-11 — Respuestas JSON pueden corromperse con caracteres especiales

**Archivo**: `src/agent_bridge/tools/review.py:167` + (CODE-03/04/05/11)
**Severidad**: MEDIUM

**Descripción**: Múltiples handlers construyen respuestas con f-strings: `f'{{"comment": "{comment}"}}'`. Si un agente envía un `comment` con `"` o `\n`, el JSON se rompe. El cliente MCP recibe texto malformado que no puede parsear. Presente en `review.approve`, `review.request_changes`, `task.claim`, `plan.update`, `_get_plan`.

**Impacto UX**: Los agentes reciben respuestas corruptas. El error no es detectable desde la TUI humana. El agente puede interpretar datos incorrectos o crashear al parsear. Los strings visibles en el chat pueden aparecer truncados o deformados. Erosiona la credibilidad de los datos del sistema.

**Recomendación**: Usar `json.dumps()` en todas las respuestas. Pydantic `model_dump(mode='json')` resolvería todos los casos automáticamente (ARCH-07).

### PROD-12 — No hay troubleshooting ni FAQ en toda la documentación

**Archivo**: `README.md` (todo el documento) + `AGENT-BRIDGE-SPEC.md`
**Severidad**: MEDIUM

**Descripción**: El README tiene 526 líneas pero CERO secciones de troubleshooting, FAQ, problemas conocidos o guía de recuperación. Escenarios comunes sin cubrir: qué pasa si el puerto 8765 está ocupado, cómo sé que el bridge funciona, qué hago si un agente no se conecta, cómo recuperarme de un crash, etc.

**Impacto UX**: El primer error que encuentre un usuario nuevo no tiene guía de resolución. La unica salida es logs de stderr (necesitan `--verbose`). La barrera de entrada es más alta de lo necesario.

**Recomendación**: Agregar sección de Troubleshooting con escenarios: "port in use", "agent not connecting", "DB locked", "TUI no muestra agentes".

## Conclusiones

### Patrón dominante
El producto está bien diseñado a nivel conceptual pero sufre de **brecha promesa-realidad** en múltiples frentes. La documentación describe una versión idealizada del sistema que no coincide con la implementación actual.

### Las 3 brechas más dañinas para la confianza
1. **`--ui-only`** miente sobre cómo se conecta el TUI (PROD-01) — el problema más grave porque el usuario opera basado en un modelo mental incorrecto.
2. **Chat "en tiempo real"** que es polling a 5s+ (PROD-02) — el humano cree tener control inmediato que no existe.
3. **@mention "no envía si offline"** que sí envía (PROD-04) — el mecanismo de seguridad documentado no funciona.

### Fortalezas
- La instalación y `init` tienen buen flujo interactivo con validación
- Las skills generadas (`dev.Skill`, `architect.Skill`) son excelentes y muy detalladas
- La TUI tiene buena discoverability de @mentions, /commands y shortcuts
- `reset` con confirmación y `--force` está bien diseñado
- El autocomplete de AgentSuggester es un detalle UX sólido
